# imgdupe

[![CI](https://github.com/dkautomation23/imgdupe/actions/workflows/ci.yml/badge.svg)](https://github.com/dkautomation23/imgdupe/actions/workflows/ci.yml)

Finds duplicate and near-duplicate images in a folder — the same picture saved
twice, re-exported, resized or recompressed — and tells you which copy to keep.

```bash
imgdupe ./photos --threshold 5 --csv duplicates.csv
```

31 662 JPEGs from a real photo folder hashed in 37 seconds on 16 threads.
Nothing is ever deleted. There is a [benchmark](#benchmark) in the repository
that rebuilds its own test folder, so the grouping can be checked, not believed.

## Why perceptual hashing

Byte-comparison finds only files that are literally identical. It misses the
case everyone actually has: the same photo at 4K and at 1920, the JPEG re-saved
by an editor, the thumbnail generated three times by three different scripts.

`imgdupe` uses a 64-bit dHash. It scales the image to 9×8 greyscale and records
whether each pixel is brighter than its right-hand neighbour. That survives
resizing, recompression and brightness shifts, and two images are "the same"
when their hashes differ by no more than `--threshold` bits.

## The chaining bug, and why grouping is complete-linkage

The first version grouped with union-find: if A matches B and B matches C, all
three become one group. Run that on a real folder and it collapses: on the
31 662-image test set it produced **one group of 912 files whose extremes were
39 bits apart** — completely different pictures, chained together through a path
of small steps. Deleting from that group would have destroyed real work.

Grouping is now complete-linkage: a file joins a group only when it is within
the threshold of *every* member. A group can therefore never span more than the
threshold you asked for, and the same run produces sane groups — 11 identical
frames here, 22 there. Two tests pin this down, including a ladder of hashes
designed to chain.

Identical hashes are collapsed first, so the O(n²) comparison runs over unique
hashes only: 222 ms for the whole 31k folder.

survives and the thumbnails are listed as extras, never the other way round.

## Deleting is your job

```bash
imgdupe ./photos --delete-script cleanup.sh
```

writes the commands out instead of running them:

```sh
#!/bin/sh
# Generated by imgdupe. NOTHING HAS BEEN DELETED YET.
# Read this file, delete the lines you disagree with, then run it.
# Frees 4.6 GB across 9935 group(s).

# group 1 - keeping .../images/144.jpg
rm -- '.../images/145.jpg'
rm -- '.../images/146.jpg'
```

Every deduplicator that deletes on its own eventually deletes the wrong file.
A script can be read, edited, and kept in version control first.

## Install

A built binary for Linux, macOS (Apple silicon) and Windows is attached to
every [release](https://github.com/dkautomation23/imgdupe/releases) — no toolchain,
no compile step:

```bash
curl -sSL https://github.com/dkautomation23/imgdupe/releases/latest/download/imgdupe-v1.0.0-x86_64-unknown-linux-gnu.tar.gz | tar xz
./imgdupe-v1.0.0-x86_64-unknown-linux-gnu/imgdupe --help
```

Each archive is built and tested on the platform it targets, not cross-compiled.

To build it yourself:

```bash
git clone https://github.com/dkautomation23/imgdupe.git
cd imgdupe
cargo build --release
./target/release/imgdupe ./photos
```

Stable Rust, single binary, no runtime. CI builds and tests on 1.98.0; the
committed `Cargo.lock` is v4, so anything older than Cargo 1.78 cannot read it.

```bash
cargo test        # 23 tests: hashing, resize invariance, chaining, ordering, overwrite guard
```

| Flag | Default | Meaning |
| --- | --- | --- |
| `--threshold` | 5 | bits that may differ; 0 = pixel-identical only, 10 = loose |
| `--flat` | off | do not descend into sub-folders |
| `--min-kb` | 0 | ignore files below this size |
| `--csv` | – | full group listing for a spreadsheet |
| `--delete-script` | – | write `rm` commands to review |
| `--force` | off | overwrite `--csv` / `--delete-script` if they already exist (otherwise refused) |
| `--all` | off | print the hash of every file |

Exit code is `1` when duplicates exist, `0` when the folder is clean.

## Benchmark

`bench/generate.py` builds its own test folder with nothing but the standard
library, so this reproduces on a clean machine:

```bash
python bench/generate.py 5000          # 6000 PNGs, 500 of them written three ways
cargo build --release
./target/release/imgdupe bench/images --threshold 5
```

Every tenth picture is written three times — full size, half size and
brightness-shifted — so a correct run must report exactly 500 groups of 3 and
nothing else. That makes the benchmark a correctness check as well as a timing:
a grouping bug shows up as the wrong group count, not as a slightly wrong number.

Measured 2026-09-17 on a 16-thread desktop CPU, Windows 11:

| Dataset | Hashing | Grouping | Result |
| --- | --- | --- | --- |
| 6 000 synthetic PNGs, 320×240 | 1.8s (3 416/s) | 16 ms | 500 groups of 3, as designed |
| 31 662 JPEGs, a real photo folder | 37s (855/s) | under 1s | — |

Real photos are larger and decode more slowly, which is the whole difference
between the two rows: the synthetic figure measures the pipeline, the photo
figure measures a working day's folder.

## Honest limits

- **It does not know what your files are for.** Frames extracted from one video
  are legitimately near-identical; the tool reports them, you decide. Start at
  `--threshold 0` on a working folder and raise it once you trust the output.
- **dHash is not rotation- or crop-proof.** A cropped or rotated copy reads as a
  different picture. That is the price of a hash this cheap.
- **Grouping is O(n²) over unique hashes.** Fine to tens of thousands of images
  (222 ms at 31k); a million-file archive needs a BK-tree, which this is not.
- **Hashing is I/O-bound, not CPU-bound.** 852 images/second here was the disk
  talking, not the 16 threads.
- **Never deletes, never moves, never rewrites.** Read-only by design.
